= Networking
:toc:

== Scope

This document defines the initial networking direction.

The protocol will evolve incrementally as the project grows.

== Principles

* The server is authoritative.
* The client sends intentions, not authoritative results.
* All network input is untrusted.
* Protocol behavior must be integration tested.
* Protocol compatibility changes must be documented.

== Initial transport

The first implementation uses WebSocket (RFC 6455) framing over TCP, with
JSON-encoded text frames. Each message is a JSON object with a `type` field
whose value is one of the message names below.

See link:adr/0002-websocket-transport.adoc[ADR 0002] for why WebSocket was
chosen over a raw TCP socket.

Initial development port:

[source,text]
----
43594
----

This choice is intentionally simple and may be revisited later through an ADR if measurements or gameplay requirements justify a change.

== Initial protocol progression

The first messages should be introduced incrementally:

[source,text]
----
HELLO
HELLO_ACK
PING
PONG
PLAYER_SPAWN
PLAYER_DESPAWN
MOVE_REQUEST
PLAYER_MOVED
CHAT_SEND
CHAT_BROADCAST
----

=== Tile movement milestone

The initial world is a `100` by `100` tile grid with zero-based coordinates.
A `MOVE_REQUEST` contains an integer destination tile:

[source,json]
----
{"type":"MOVE_REQUEST","x":12,"y":34}
----

The server rejects destinations outside `0..99` on either axis. Accepted
destinations do not immediately change player position. On each five-hertz
server tick, the server advances a moving player by one orthogonal tile and
broadcasts the resulting `PLAYER_MOVED`. The baseline deterministic path
resolves the X axis before the Y axis; obstacle-aware pathfinding can replace
that policy when world collision is introduced.

Do not add messages before they are required by a milestone.

== Protocol versioning

The protocol must expose an explicit version from the first real handshake.

Example:

[source,text]
----
PROTOCOL_VERSION = 1
----

Unsupported versions should be rejected cleanly.

== Validation

The server must validate:

* message type
* payload size
* numeric ranges
* referenced entity identifiers
* state preconditions

Malformed messages must not crash the server.

== Testing

Networking integration tests should use lightweight non-graphical clients where practical.

Example flow:

[source,text]
----
start server
-> connect test client
-> send HELLO
-> receive HELLO_ACK
-> send PING
-> receive PONG
-> disconnect
----

Later tests should cover multiple concurrent clients and gameplay flows.

The first such test, `tools/test_movement_milestone.py`, starts the built
server, connects two lightweight Python WebSocket clients, and asserts that
one client's `MOVE_REQUEST` produces the expected one-tile-per-tick path for
the other client. It also verifies that an out-of-bounds destination does not
move the player. It does not use `PING`/`PONG` yet, since that message pair
isn't required by this milestone.

The chat milestone test, `tools/test_chat_milestone.py`, starts the built
server, connects two clients, sends `CHAT_SEND` from one, and asserts the
other receives `CHAT_BROADCAST` with matching sender and text.
